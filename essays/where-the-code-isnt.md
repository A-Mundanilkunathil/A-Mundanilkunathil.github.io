## An honest answer

Software engineering by itself does not actually pull me in, and I think that is a weird thing to admit in an essay about my interest in software engineering. With the advent of AI, a lot of tools have taken over the code writing part of the job. So for me the interesting question is no longer how to write the code. What really interests me is the places where code is not readily available, the industries where software engineering has not been as accessible. Agriculture. Construction. Industries where people have always been doing things a certain way, mostly because building for them is not as profitable. Making an app for construction is never going to be as profitable as making something for a company like Meta, so nobody does it, and those industries just stay the way they are. What drives me about software engineering is being able to take that skill set into those different industries.

## The framework transfers

My own experience backs this up. Most of my projects are in robotics, and robotics is obviously a different discipline from software engineering. But the framework is very similar. If I did not have a background in software engineering and just thinking like an engineer, I do not think I would have been able to do the projects I did at work and at startups. You can pick up a new skill or a new topic and attack the problem the same way you would attack a software problem. That is the actual value of this degree to me. It is not the syntax of any one language, it is a way of approaching problems that you can carry into whatever industry you end up in.

## What I need to get better at

The skill I am honestly trying to develop right now is executing projects from start to finish. I am very good at starting projects, and I can see them through the toughest phase in the middle. But near the end I start weaning off. I do all the hard stuff at the beginning, burn myself out, and by the end I am looking at the project thinking it does not seem that impressive anymore, and I do not even know what features I want to add. So a big one for me is figuring out how to pace myself as an engineer instead of front loading all the effort.

On the technical side, syntax recall when learning a new language is something I am still getting better at, which my WOD estimation logs in this class show pretty clearly. Logic under time pressure I am more okay with. One thing I have realized from practicing problems is that the brute force solution is usually the easiest solution but not the most optimal one, and coming up with better solutions is partly a memorization thing. If you have seen enough solutions, you start to recognize how to approach a new problem with different tactics. I want to keep building that library in my head.

## Before I graduate

The experience I really want before I graduate in May 2027 is working on an end to end product all the way to the end. I have worked at multiple startups now, and I never get to see the product finished. Either I leave or my term ends before the project is done. Startup culture is always about the proof of concept and the prototype, so actually finishing something, knowing it end to end, and then maintaining it and adding features afterward is a genuinely rare experience there. That is the experience I want: to be able to say I finished something completely, and then to live with it. Given where I want to take this skill set, into industries where the software does not exist yet, being someone who can carry a product from nothing to done to maintained is exactly the engineer I am trying to become.
